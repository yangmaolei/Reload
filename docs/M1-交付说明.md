## 1. 怎么启动

```powershell
# 方式一：源码运行
& "C:\Users\yang\.dotnet-sdk\sdk8\dotnet.exe" run --project .\src\GameSaveSync.App

# 方式二：自包含单文件（已发布）
.\publish\win-x64\GameSaveSync.exe
```

首次启动会创建 `%LOCALAPPDATA%\GameSaveSync\{gamesavesync.db, objects, manifests, logs}`（per-user，不需要管理员权限）。

操作路径（3 步）：

1. **设置** 页填 WebDAV 地址 / 用户名 / 应用密码 / 远程根目录 → 点「测试连接」（会 MKCOL 建目录、写探针、读回、删除）→「保存配置」。
2. **游戏** 页点「添加游戏」→ 填名称 + 选存档目录（可多个）+ 排除规则（默认 `*.log; *.tmp`）。
3. 选中游戏点「立即备份」→ 快照出现在右侧时间线；选中任一快照点「恢复到此时点」→ 看计划 → 确认执行。

冒烟结果（Release 单文件版实机启动）：

```

2026-10-30 21:07:47.674 [INF] 未配置 WebDAV，快照只保存在本地
主窗口标题：GameSaveSync — 游戏存档备份（MainWindow 已创建，XAML 资源解析通过）
```

补充的"编外"验证（同一次运行内）：

- 上传顺序：请求日志断言所有 `PUT objects/*` 早于清单 `PUT`，且清单走 `临时名 PUT + MOVE`。
- 对象被截断：恢复前校验失败并给出明确错误，目标文件保持原样（不会被半截数据覆盖）。
- 目标文件被独占：重试 3 次后列入失败清单，其余文件继续恢复，临时文件清理干净。
- 令牌缺失 / 目录被删：`NeedsRelocateException` + `needs_relocate=1`，不产生空快照、不崩溃。
- 未配置 WebDAV：快照仍落盘，`pending` + "尚未配置 WebDAV"。
- emoji/中文存档根上传后，远端清单里 `roots[0].token` 仍是 `%SAVEDGAMES%…`。

## 4. 性能数据（诚实版）

在同机做的裸 IO 基线：`create + write + rename` 2000 个小文件 = **2.06 ms/文件**（本机磁盘/杀软较慢）。
引擎实测 5000 文件 = **14～22 s（≈2.9～4.3 ms/文件）**，多次运行波动明显（同一台机器上裸 IO 基线也随负载从 2.0 漂到 3.5 ms）。引擎自身开销约 **0.85～1.2 ms/文件**，其余是文件系统与杀软。
按此推算 10 万文件约 5 分钟 —— 距方案里"NVMe 上 ≤3 分钟"的目标还差一截，瓶颈在每文件一次 CAS 落盘（无法避开"存档 → 对象"的复制），后续可做：小文件打 pack（M5）、扫描与哈希流水线并行。

`FlushFileBuffers` 实测每次约 **6 ms**，因此默认关闭（见下节偏差 1）。

## 6. 与方案的偏差与已知限制（请先看这里）

1. **fsync 默认关闭**（`FileSystemObjectStore.DurableWrites = false`，`RestoreService.DurableWrites = false`）。
   理由：每文件 fsync 实测 6 ms，5000 文件要多花 30 s，直接把"备份 ≤800 ms"和"10 万文件 ≤3 分钟"打穿。
   现状保证的是：**进程被杀 / 崩溃不会留下半截对象**（临时名 + rename 已覆盖，验收 6 通过）；极端**断电**仍可能丢最近写入的数据。
   要抗断电就把它设为 `true`（代码里一处开关，UI 待 M2 暴露）。
2. **绝对路径兜底**：用户选的目录若不在任何标准根下（如 `D:\Saves`），`SaveRoot.IsTokenized=false` 并原样存绝对路径，UI/日志会警告"跨机需重新定位"。
   这是对"禁止存绝对路径"的**有意妥协**——否则这类游戏根本无法添加。
3. **自签名证书是"手填指纹"而非"点击信任"**：`WebDavOptions.TrustedCertificateThumbprint` 只接受用户显式输入的 SHA-256 指纹，未匹配一律拒绝（不做全局跳过）。缺一个"拉证书 → 展示 → 确认"的对话框，列为 M2 体验项。
4. **空闲内存未达标**：Release 单文件实机启动后 工作集 ~259 MB / 私用 ~171 MB，高于方案里"<120 MB"的目标。原因是自包含单文件 + WPF + 压缩包解压。M2 需要：关压缩/ReadyToRun、延迟加载 DataGrid、必要时改 framework-dependent。
5. **M1 不做内容一致就跳过**：同一内容连续两次手动备份会产生两个快照（内容相同、对象复用）。M2 的"内容与上一快照相同则不产生新快照"未实现（避免误伤用户手动打点）。
6. **删除是可选项**：恢复默认会删除"快照里没有、目录里有"的文件（真正回到那一刻）；`RestoreService.DeleteExtraneousFiles=false` 可关闭。M1 UI 未暴露该开关。
7. **目录级空文件夹不恢复**：清单只记文件，恢复后不会重建空目录（游戏存档极少依赖空目录）。
8. **单实例**用 `Local\GameSaveSync.SingleInstance` 命名 Mutex；第二实例只提示、不唤起已有窗口（M2 托盘阶段再补窗口唤起）。

## 7. 下一步（M2）建议顺序

1. 进程监控（WMI `Win32_Process*Trace` + 2 s 轮询兜底）→ `post-exit` 快照。
2. 三层漏斗（FileSystemWatcher 64 KB + `FILE_ID_INFO` + BLAKE3）→ 去抖 3 s → 稳定性判定（400 ms 复检，200/400/800/1600/3200 退避）。
3. outbox 表驱动 + 指数退避 + 启动重放（把 `UploadService` 的扫表换成队列）。
4. GFS 保留策略 + 引用计数减删。
5. 托盘 + 开机自启 + 空闲快照（`IDLE_PRIORITY_CLASS`、单并发、1 MB 块、块间 50 ms）。
