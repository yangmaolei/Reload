### 实现位置

| 文件 | 改动 |

| `App/Views/Pages/GamesPage.xaml` | 卡片结构改为 Grid 套 Button 套 Border；CheckBox 作为 Grid 兄弟节点浮在卡片左上角；新增批量操作条 |

### 关键逻辑

**多选与单选是两套独立状态。**

- 单选：`SelectedGame`，决定右侧详情页显示谁
- 多选：`IsChecked`，只影响批量备份/导出

点卡片进详情不会清掉勾选，勾选也不会改变详情页显示。两者互不干扰。

**CheckBox 必须放在 Button 外面。**

卡片整体是一个 `Button`（点击进详情）。如果把 CheckBox 放进 Button 的内容里，点击复选框会**同时**触发卡片的 `Command`，用户勾选后立刻被弹进详情页。改成：

```xml
<Grid Width="228" Margin="8">
    <Button Command="SelectGameCommand">...卡片内容...</Button>
    <CheckBox IsChecked="{Binding IsChecked}" />   <!-- 兄弟节点，命中测试优先 -->
</Grid>
```

Grid 的命中测试按子元素**逆序**（后声明的先测），所以 CheckBox 在上层，点击不会落到 Button 上。

**刷新列表不丢勾选。**

`LoadAsync` 会重建全部 `GameListItemViewModel`。重建前先记住已勾选的游戏 ID，重建后逐个恢复。注意恢复要在 `CheckedChanged` 订阅**之后**设置 `IsChecked`，否则事件不触发、计数不同步。

**计数同步。**

每个条目勾选变化 → `OnItemCheckedChanged` → `RecountChecked()` 重算 `CheckedCount` → `CheckedSummary` 派生文案（"未选择" / "已选 1 个" / "已选 N 个"）。

### 状态反馈

- 有勾选时，列表顶部出现一条深色圆角操作条
- 左侧：「已选 N 个」+「全选 / 取消全选」+「清空选择」
- 右侧：「一键备份所选」「一键导出所选」
- 无勾选时整条操作条 `Collapsed`（用 `BoolToVisibility`，不用 `InverseBool` —— 后者返回 bool，绑到 Visibility 上会静默失败）

### 目录结构

**一键备份所选**（导出到目录）：

```
<用户选择的目录>/
  测试游戏丙_0b794bfe/          ← 游戏名_游戏ID前8位
    1_测试游戏丙/               ← 序号_存档根名
      slot0.sav
      slot1.sav
      config/opts.ini           ← 子目录结构原样保留
  测试游戏乙_e883acbd/
    1_测试游戏乙/
      slot0.sav
```

**一键导出所选**（打包 zip）：同样的结构，压缩包内按游戏分目录。

- 子目录名带 **ID 前 8 位** → 同名游戏不会互相覆盖
- **保持原文件、原相对路径** → 用户拿到导出目录能直接放回游戏的存档位置
- 应用每个存档根的 include/exclude 规则（`*.log` 之类会被排除）

### 失败与已存在的处理

| 场景 | 处理 |
|---|---|
| 目标目录已存在 | 区分「覆盖」与「跳过」，不静默把旧内容混进新内容。UI 上备份走覆盖，失败时明确报「目标目录已存在」 |
| 单个游戏存档目录失效 | 该项报失败「本机找不到该游戏的存档目录（可能需要重新定位）」，**其他游戏照常导出** |
| 一个可解析存档根都没有 | 明确报失败，而不是报「成功但 0 个文件」——后者会让人误以为存档是空的 |
| 单个文件读失败 | 只跳过该文件并记日志，不让整个游戏失败 |
| 游戏记录已删除 | 报「游戏记录不存在」 |

### 状态反馈

导出完成后弹「批量导出结果」对话框：

```
输出位置：C:\Users\...\uitest\batch-export..zip
合计：成功 2/2，共 8 个文件、1.06 KB
测试游戏丙：5 个文件，768 B
测试游戏乙：3 个文件，320 B
```

逐项列出成功/失败与原因。主窗口另有 `BatchResultText` 常驻提示（不随全局状态栏 10 秒消失）。

### 为什么要有 BatchOperationPlanner

`MainViewModel` 有 20 个构造参数，直接构造来测太重。把「选中了哪些游戏 → 该做什么 → 结果怎么算」剥到 `BatchOperationPlanner`，它只依赖 `IGameRepository` + `IBatchSaveExporter` + `IAppLogger`，可以轻量单测。

### 真实生效的判定

只看「注册表里有没有这个键」是不够的 —— 程序换了位置、exe 被删了、或者被别的软件改过，键还在但开机根本起不来。

`GetStatus()` 依次检查三条，全满足才算 `IsEffective`：

1. 登记项存在
2. 登记的路径指向的文件**真实存在**
3. 该路径与**当前运行的 exe** 是同一个（否则是「别人的旧路径」）

不满足时给出具体原因：

- 「自启动指向的程序已不存在：C:\不存在的路径\Reload.exe」
- 「自启动指向的是另一个副本：C:\...\旧版本\Reload.exe」

### 三种方式

| 方式 | 实现 | 登记位置 |
|---|---|---|
| 关闭 | 两种方式都清掉 | — |
| 注册表启动项 | `HKCU\...\Run` 值 | `Reload` |
| 启动文件夹快捷方式 | WScript.Shell 创建 `.lnk` | `shell:startup\Reload.lnk` |

**切换方式时自动清掉另一种的登记项**，避免开机双开。这点已真机验证：注册表 → 启动文件夹切换后，注册表项变空、启动文件夹出现 `Reload.lnk`；再切回「关闭」，两边都清干净。

### 设置页

- 三个单选按钮：关闭 / 注册表启动项 / 启动文件夹快捷方式
- 状态提示行：显示检测结论（已生效 + 路径 / 未生效 + 原因）
- 「重新检测」按钮：手动重新扫描

### 测试安全性

`AutoStartService` 的注册表值名可注入（`new AutoStartService("ReloadTest-xxx")`）。集成测试用独立值名，**绝不碰用户真实的 `Reload` 自启项和 `Reload.lnk`**，测完自动清理。

## 四、顺带修的两个 Bug

### `OpenFolderDialog.ShowDialog(Owner)` 静默失败

`Microsoft.Win32.OpenFolderDialog`（.NET 8 新增）内部走 Win32 的 `IFileDialog`。WPF 的 `ShowDialog(Window owner)` 重载对它是**能编译但不弹窗**——用户点「一键备份所选」毫无反应，日志里也什么都没有。

改用无参 `ShowDialog()`，实测可靠。

（`SaveFileDialog.ShowDialog(Owner)` 是经典 Win32 对话框，带 owner 正常工作，未改。）

### 对话框异常被静默吞掉

`PickFolder` / `PickSaveFile` 原来在 `try` 块**外面**调用。`RelayCommand` 的异常会被静默吞掉 —— 用户点了按钮没反应，也没有任何错误提示。

现在包进 `try`，失败时记日志并弹「无法打开保存对话框：xxx」。

## 六、已知限制

- 「一键备份所选」用的 Win32 文件夹对话框在自动化环境下无法可靠地关闭（BM_CLICK、Enter、鼠标点击均试过），因此该路径的 UI 端到端验证未完成；其底层逻辑由 19 条单元测试在真实文件系统上覆盖，目录对话框本身确认能正确弹出。
- 批量导出不递归进符号链接/联接点（与 `IFileSystem` 的既有语义一致），避免目录环。
