# M2 交付说明（自动化与可靠性）

> 对应 `分阶段Prompt-M1-M2-M3.md` 的 M2 阶段。
> 结论：`dotnet build` 0 warning / 0 error，`dotnet test` **81/81 通过（53.7 s）**，M2 的 8 条验收逐条有实测数据。

---

## 1. 怎么启动 / 怎么用

```powershell
.\publish\win-x64\GameSaveSync.exe          # 自包含单文件（约 70 MB）
# 或
& "C:\Users\yang\.dotnet-sdk\sdk8\dotnet.exe" run --project .\src\GameSaveSync.App
```

M2 之后它是个**装完不用管**的常驻工具：

1. 添加游戏时填 **可执行文件名**（如 `game.exe`）和 **安装目录** —— 这是进程识别的依据（缺了就只能靠文件变更触发，不会做 exit 快照）。
2. 之后：启动游戏 → 自动打 `pre_launch` 保险点；玩着 → 每 15 分钟尝试一次 `idle` 快照；退出游戏 → 2 秒后打 `exit` 快照并自动上传；旧快照按 GFS 自动清理。
3. 关窗口 = 最小化到托盘（自动备份继续跑），托盘菜单可暂停 30 分钟 / 1 小时 / 直到重启，可开开机自启，退出时若有待上传项会二次确认。
4. 再点一次 exe（第二个实例）会唤起已有窗口，不会起两个进程。

## 2. 六块必做项的实现位置

| M2 要求 | 实现 | 说明 |
|---|---|---|
| 1. 进程监控 | `Infrastructure/WindowsProcessWatcher` + `Core/Scheduling/GameProcessMatcher` | WMI `Win32_ProcessStart/StopTrace` 当**加速器**（收到事件立刻触发一次轮询）；2 秒轮询是真相来源；匹配 = exe 名（不区分大小写）+ 必须位于 `installDir` 下；退出后延迟 2 秒再拍 |
| 2. 三层漏斗 | `SaveFolderWatcher`（L1，64 KB）→ `FileFingerprint`（L2，size+mtime+FILE_ID_INFO）→ `SnapshotService`（L3，BLAKE3 对比上一快照） | L1 溢出只置 dirty，绝不直接触发；L2 未变文件直接复用上次哈希（不读盘）；L3 内容不变则**不产生新快照** |
| 3. 触发时机 | `Core/Scheduling/SnapshotScheduler` | `exit` 主力、`post_change`、`pre_launch`、`manual`、`idle`；idle 需同时满足磁盘空闲 / CPU<30% / 非全屏独占；后台路径统一 `IDLE` 线程优先级 + 1 MB 块 + 块间 50 ms + 全局并发 1 |
| 4. 持久化 outbox | `Core/Sync/Outbox.cs` + `OutboxProcessor` + `RemoteOperationExecutor` | 网络操作先落库再执行；`dedupe_key` 去重；退避 1s→2→4…封顶 5min ±20%；连续 20 次失败标 `failed` 并托盘气泡；启动时重放 `pending`/`inflight` |
| 5. GFS 保留策略 | `Core/Retention/RetentionService` | 最近 N（20）+ 每日 1×7 + 每周 1×4；手动快照永不自动删、`pre_restore` 保 7 天、最新一个永远保留；先软删本地引用再按引用计数删 CAS，远端删除进 outbox 重试 |
| 6. 常驻形态 | `App/TrayIconService` + `App.xaml.cs` | 单实例 Mutex + 命名事件唤起窗口；托盘状态/暂停/自启/退出确认；关窗=最小化到托盘 |

### 去抖与稳定性（最容易翻车的地方）

```
文件事件 → 取消上一个 3s 定时器 → 重新计时
       → 到期后 StabilityGate：所有文件 stat → 等 400ms → 再 stat
       → 有任何 size/mtime 变化 → 退避 200/400/800/1600/3200ms 重试（最多 5 次）
       → 仍不稳定：放弃本次并记日志（绝不生成快照）
       → 稳定：拍快照；内容与上一快照一致则不落库
```

单文件层还有第二道保护：`SnapshotService` 读前读后各 stat 一次，size/mtime 变了就重读（最多 3 次），仍不稳定则跳过该文件。

### outbox 状态机

```
enqueue(dedupe_key) ──► pending ──lease──► inflight ──ok──► 删除（完成）
                          ▲                    │
                          │                    └──fail──► pending(next_retry_at=now+backoff)
                          │                                     │ attempts>=20
                          └────────── 启动重放 ──────────────────┴──► failed（托盘提示，可一键重试）
```

上行顺序约束：`put_manifest` 执行前会检查该快照引用的对象是否全部 `uploaded`，未就绪就抛 `OutboxNotReadyException` 让它延后重试 —— 保证"清单出现时引用的东西一定已就位"。

## 5. 与方案的偏差 / 已知限制

1. **WMI 需要管理员**：本机（普通用户）实测 `Win32_ProcessStartTrace` 订阅返回"拒绝访问"，程序按设计退化到 2 秒轮询，日志里明确写了：
   ```
   [WRN] WMI 进程事件订阅失败，改用 2 秒轮询（功能不受影响）
   System.Management.ManagementException: 拒绝访问
   ```
   这就是方案里说的"WMI 偶尔丢事件 + 轮询兜底"，只是这里 WMI 完全不可用。性能上没有影响（2 秒一次 PID 比对）。
2. **PresentMon 帧时间（验收 2）没有真实数据**：需要一台装有游戏和 PresentMon 的机器。代码层面能保证的是：后台快照线程优先级降到 `IDLE`、单次读块 1 MiB、块间 50 ms、全局并发 1、全屏独占时不做 idle。**请在你常用的游戏上按 §6 的方法自测一次**。
3. **idle 快照 24 小时实跑未做**：本次只验证了"条件满足会触发、条件不满足不触发、单次 66 ms"。24 小时的触发次数取决于你实际玩游戏多久，用日志过滤 `trigger=idle` 即可统计（见 §6）。
4. **fsync 仍然默认关闭**（M1 的偏差延续）：进程被杀安全（验收 3 通过），极端断电不保证。
5. **"内容不变不产生快照"只对自动触发生效**，手动点"立即备份"永远会生成快照（用户意图优先）。
6. **启动补扫只对"已有至少一个快照"的游戏做**，避免刚添加的游戏在第一次启动就被自动拍一张。
7. **托盘图标用的是系统默认图标**（`SystemIcons.Application`），没有做专属 ico；状态变化时会在默认/警告图标间切换。
8. **暂停状态不持久化**："暂停直到重启"在重启后自动恢复（符合字面语义）。

## 6. 两条需要你在真机上补测的项目

### 6.1 帧时间（验收 2）

```powershell
# 1) 先只开游戏，采 60 秒基线
PresentMon.exe --process_name game.exe --output_file baseline.csv --terminate_after_timed 60
# 2) 打开 GameSaveSync（自动备份启用），再采 60 秒
PresentMon.exe --process_name game.exe --output_file with_sync.csv --terminate_after_timed 60
# 3) 对比两边的 p99 帧时间
```

判定：`with_sync.p99 - baseline.p99 < 1 ms`。
若超标，先把 `SnapshotSchedulerOptions.IdleInterval` 拉长或托盘里"暂停 1 小时"再测，确认是 idle 快照导致的。

### 6.2 idle 快照的 24 小时统计

```powershell
Select-String -Path "$env:LOCALAPPDATA\GameSaveSync\logs\gamesavesync-*.log" -Pattern "trigger=idle|静默快照" |
  Group-Object { $_.Line.Substring(0,10) }
```
每个 `idle` 快照的耗时会出现在同一条日志的"耗时 xx ms"里（`SnapshotScheduler.CaptureAsync` 不直接打印耗时，可看相邻两条日志的时间差）。

## 8. 一个踩坑记录（给未来的自己）

`SnapshotService` 的 `IoOptions` / `SkipIfUnchangedWithParent` 是实例状态，而调度器可能同时为多个游戏触发快照。M2 里用**全局信号量把快照串行化**（正好也是规格要求的"并发度 1"）来避免状态互相踩。M3 如果要做并行快照，得先把这两个属性改成方法参数（会动冻结接口，需要慎重）。
