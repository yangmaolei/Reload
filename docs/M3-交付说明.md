# M3 交付说明（多设备）

> 对应 `分阶段Prompt-M1-M2-M3.md` 的 M3 阶段。
> 结论：`dotnet build` 0 warning / 0 error，`dotnet test` **105/105 通过（64.6 s）**，M3 的 7 条验收逐条有实测数据。

---

## 1. 两台机器怎么用

真实场景（两台 Windows）：

1. A 上装好、连好 WebDAV、添加游戏并备份一次 → 云端出现 `index.json`、`devices/<A>.json`、`games/<gameId>/snapshots/*.json`、`objects/*`。
2. B 上装同样的程序、连同一个 WebDAV 地址与账号 → 启动后自动：
   - 注册 `devices/<B>.json`；
   - 每 60 秒 `GET index.json`（带 `If-None-Match`，绝大多数是 304）；
   - 发现本机没有的 `snapshotId` → 拉清单 + 缺失对象（逐个校验 BLAKE3）→ 游戏卡片自动出现。
3. B 的界面里游戏会被标成「需重新定位」（因为它的存档目录在本机不存在）→ 点「重新定位」，把该存档根映射到本机目录（映射存在 `games.path_overrides`，不猜路径）。
4. 选快照 → 恢复到此时点；恢复前仍会自动打 `pre_restore` 保险点。

两台都改过同一个游戏时：卡片显示「冲突」，点「处理冲突」→ 并排看到 A/B 两侧（来源设备、时间、文件数、大小、相对共同祖先的 +/~/-）→ 选一边，或「导出两侧 zip」慢慢比。**不管选哪边，两边的快照都还在云端。**

## 2. 远端协议实现

```
/GameSaveSync/
  vault.json                                版本 / 加密开关（M1 已建）
  index.json                                全局索引（唯一需要并发控制的文件）
  devices/<deviceId>.json                   {id, name, lastSeenAt, seq, appVersion}
  games/<gameId>/snapshots/<ts>-<sid>.json  快照清单
  objects/<hh>/<hash>                       内容寻址对象（不可变）
```

`index.json` 结构（严格按方案）：

```json
{ "version": 1, "updatedAt": 123,
  "games": { "<gameId>": { "seq": 5, "snapshotId": "...", "deviceId": "...", "updatedAt": 123, "conflict": false } } }
```

### 上行顺序（已强制）

`put_object` → `put_manifest` → `put_index`，全部走 outbox，按 id FIFO 执行：

- `put_manifest` 执行前检查该快照所有对象都已 `uploaded`，否则抛 `OutboxNotReadyException` 延后；
- `put_index` 执行前检查快照 `remote_state=uploaded`，否则同样延后。

这样 `index.json` 出现时，它指向的清单和对象一定已经在远端。

### 下行

只轮询 `index.json` 一个文件：`GET` + `If-None-Match`，304 直接结束；只有发现本机未知的 `snapshotId` 才拉清单与对象。
唯一会列目录的地方是"按 sid 找清单文件名"和"索引损坏后重建"，**绝不逐文件 PROPFIND**。

### 一个必须说明的语义修正：seq 是 Lamport 时钟，不是各设备独立计数器

方案写的是"seq 为每设备单调递增计数器"，合并规则却要比较两台的 seq。如果两台都从 1 开始，新设备的第一次发布永远不可能大于远端已有值（例：A 已发到 seq=1，B 首发也是 1 → 按规则 B 会被远端覆盖，B 的快照虽然上传了却永远进不了索引）。

实现改成：**发布时 `seq = max(本机已用, 远端该游戏的 seq) + 1`**。
- 仍然是"每设备单调递增"（只增不减）；
- 跨设备可比（谁在谁之后发布，seq 就更大）；
- 冲突判定仍是方案里那四条规则，一行没改。

这是本次唯一一处对协议文字的偏离，测试里用 `Publish_WritesIndexAndIncrementsSeq` 和 C2 两条用例覆盖。

## 3. 冲突合并状态机（可直接对照代码 `IndexMerger.Merge`）

| # | 输入组合 | 结果 | conflict 标记 |
|---|---|---|---|
| 1 | 只有远端有条目 | 用远端 | 继承远端 |
| 2 | 只有本地有条目 | 用本地 | 继承本地 |
| 3 | 远端 `deviceId == 本机` | seq 大者胜（都是自己的历史） | 各自原值 |
| 4 | 本地 seq > 远端 seq，且两快照有父子关系 | 用本地（正常推进） | false |
| 5 | 本地 seq > 远端 seq，且两快照无父子关系 | 两边快照都保留；`snapshotId` 取 `created_at` 较新者 | **true** |
| 6 | 本地 seq ≤ 远端 seq | 用远端（别的设备更新） | 继承远端 |

补充约定：
- 合并结果永远包含双方所有游戏的并集，**任何分支都不删除快照**；
- `conflict` 只影响"默认推荐哪个版本"，两个快照的清单与对象都还在云端；
- 判定"父子关系"用本地时间线图（`snapshots.parent_id` 向上走最多 500 层，双向查询）；
- 412 重试最多 5 次，每次重新 `GET` → 合并 → `PUT`，退避带 60~140 ms 抖动；5 次仍失败则抛给 outbox 继续重试（指数退避到 5 分钟封顶）。

单测：`M3IndexTests` 里 `Rule1` ~ `Rule6` 六个用例逐条对应上表。

## 4. 7 条验收：实测结果

`tests/GameSaveSync.Tests/M3AcceptanceTests.cs`（另加 C8 设备注册）。两台"机器"用同一进程内两个独立数据目录 + 同一个 WebDAV 服务器模拟。

| # | 验收项 | 结果 | 实测数据 |
|---|---|---|---|
| 1 | A 备份 → B 60 秒内看到 → B 恢复 → 逐字节相同 | ✅ | B 轮询 1 次导入 1 个快照，恢复写入 2 个文件、失败 0，2 个文件的 BLAKE3 全部一致；默认轮询间隔 60 s |
| 2 | A 断网改档 → B 改同一游戏并上传 → A 恢复网络：两快照都在云端、index 标 conflict、outbox 无无限重试 | ✅ | `index.conflict=True`；远端清单 3 个（基线 + A + B，一个不少）；A 的 outbox 待办 **0**；重试 1/1 成功 |
| 3 | 模拟 412：PUT 前被别的设备改过 index | ✅ | 注入一次 412 → 自动重读合并重试，最终索引里 **2 个游戏**（别的设备的条目没被吞），A 的条目 `seq=3` |
| 4 | B 没有安装目录 → needsRelocate → 指定目录后能恢复 | ✅ | 重定位前 `CanExecute=False`；映射后写入 1 个文件，内容哈希与 A 一致 |
| 5 | 远端对象被截断 → 校验失败、提示明确、可重传、不写坏文件 | ✅ | 截断后 B 导入 `imported=0`、快照未入库、CAS 残留 **0** 个对象、日志含校验失败；恢复正确对象后重试导入成功 |
| 6 | index.json 被写坏 → 不崩溃、重建索引 | ✅ | 写入 `{ this is not valid json ###` → `rebuilt=True`，重建出 1 个游戏、索引恢复合法，B 随后成功导入 |
| 7 | 连续 24 小时轮询量与预期相符 | ✅（按比例外推） | 10 次轮询 = **10 个 GET**，其中 **9 次 304**；默认 60 s → **24 小时 1440 次请求**（1 次全量 + 1439 次 304） |

另外两条补充用例：
- **冲突视图**：并排两侧（设备、时间、文件数、大小、相对祖先 +0 ~1 -0），选择后 `conflict` 清除；
- **导出 zip**：导出内容与快照文件一致（`save.sav` 1 项）。

## 6. 服务商适配层（M3 第 4 条）

`WebDav/Providers/ProviderAdapter.cs`：

| 适配器 | 行为 |
|---|---|
| `GenericProviderAdapter` | 单次 PUT；失败由 outbox 重试 |
| `NextcloudChunkedAdapter` | 大对象走 `<path>-chunking-<id>` 目录分片 PUT + `MOVE .file` 收尾；**MOVE 失败自动回退单次 PUT**（流可 Seek 时） |
| `RateLimitedProviderAdapter` | 串行 + 最小请求间隔（坚果云这类），与 `WebDavOptions.RateLimited` 配合 |

统一处理的坑：不支持 MOVE → 退化直接 PUT（读取侧校验 hash）；MKCOL 不递归 → 逐级创建；不返回 ETag → 用 `lastModified` + 内容哈希兜底（并把 `If-Match` 降级为无条件 PUT + 写前重读）；HEAD 不支持 → `GET Range: bytes=0-0`。

测试：`NextcloudProvider_UsesChunkedUploadAndLandsExactContent`（1 MB / 256 KB 分片 → 4 片 → 组装后内容逐字节一致）、`GenericProvider_UploadsInOnePut`。

## 7. 偏差与限制

1. **seq 语义**（见 §2）：改成 Lamport 时钟。这是必要的偏离，否则新设备永远发布不进去。
2. **"24 小时连续运行"** 用 10 次轮询 + 默认间隔外推（C7），没有真的等 24 小时；请求量公式可验证（每次轮询恰好 1 个 GET）。
3. **两台机器是同一进程内模拟**：两个独立数据目录 + 独立 SQLite + 独立 WebDAV 客户端，共享一台进程内服务器。真实跨机的差异主要是网络延迟与系统时钟，而本方案不依赖墙上时钟排序（用 `seq` + `parent_id`）。
4. **冲突差异只到"数量"级别**：给出 +/~/- 计数，没有逐文件列表（M4 的差异视图会补）。
5. **重新定位是整根映射**：一个存档根映射到一个本机目录，不支持"子目录级别的部分映射"。
6. **远端清单文件名靠 sid 匹配**：`ListAsync` 一次目录（PROPFIND Depth:1）后按 `-<sid>.json` 找，属于方案允许的"重建/发现"路径，不在日常热路径上。
7. **删除远端快照**（保留策略）仍是 outbox 的 `delete_manifest`/`delete_object`，M3 未改变其语义；多设备下如果另一台还引用该对象，靠 refcount 本地判定，远端可能出现"对象被删但清单还在"——M4 需要把 refcount 也纳入索引（列在待办）。
